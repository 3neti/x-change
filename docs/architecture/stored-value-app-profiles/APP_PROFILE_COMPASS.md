# App Profile Compass

1. An app profile chooses a primary home and navigation. Journeys express business purpose; journey kinds express reusable primitives.
2. One primary profile and zero or more additional profiles may coexist in a host. Shared journey keys resolve once; conflicting definitions fail compilation.
3. All packaged profiles compile and every advertised journey resolves to a usable v1 route and adapter before activation.
4. YAML and environment selection never create a financial permission. Actions use their existing server-side authorization and approval gates.
5. Direct authorization is the default for consequential journey actions. Maker-checker is an explicit policy, not a second journey. Read-only journeys have no approval action.
6. Existing Pay Code, campaign, Form Flow, voucher, Treasury, and x-journal boundaries remain authoritative. Profiles compose those engines rather than fork them.
7. A host may change its primary profile without rewriting issued vouchers or active collection policy. Frozen financial instructions remain attached to their original transactions.
8. Unsupported specialized domains are stated accurately: the v1 adapters do not imply FX pricing, a loan book, cross-border rails, or insurance underwriting.
